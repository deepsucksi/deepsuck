# DeepSuck 评测（v0.5）

> 评测时间：2026-10-18（北京时间）。所有数字都可以用下面的命令复现（固定随机种子）。v0.5 的前后对比都是在同一台机器上实跑得到：“改前”= commit `e4b6dfa` 的规则，“改后”= 本版规则。

两部分：

1. **骗子对练**：主指标是大模型扮演骗子（`eval/llm_scammer.py`，默认关闭）的起疑挂断率、拖延轮数与提取率；脚本化、不用大模型的规则骗子模拟器（`python -m deepsuck.sim`）降为次要回归项，衡量拖延与提取是否退步，`--reveal hard` 让骗子改用更难的去武装写法；
2. **话术分类器**（`python eval/teleantifraud_eval.py`）：在 TeleAntiFraud 公开文本对话上做“诈骗 vs 正常来电”二分类。

v0.6 在第 1 部分新增：骗子台词改用真实话术语料（`--lines corpus`），以及提取器在噪声、数字混淆、跨回合拆分下的提取率与误拼率（`python eval/noise_eval.py`）。

**新暴露的问题与修复**（JS / Python 同步，规则在 `site/assets/core/extractors.json`）：

1. 三点省略 / 停顿带空格拆不开：中文数字串之间的分隔原先固定至多 2 个（“六二二二...零二零二”），数字分组至多 3 个（“6222... 0212”是 4 个）→ `digitJoin.maxSep` 改为 4，中文数字、钱包分段、拼接片段都跟随它；
2. 座机 / 400 热线完全不认分组停顿（landline 只认 `0xx-xxxxxxxx`）→ 能拼接座机（010 / 02x + 8 位，0[3-9]xx + 7/8 位，用户号 2–8 开头）与 400 / 800；前面紧挨订单号 / 工号 / 验证码等不算，两位一组（开奖号码 03、15、22…）不拼，跨回合拼出的座机需电话上下文；
3. 卡号跨回合的误报与漏报：后半段像手机号（“1776…1855…023”，模拟器电话误报 39 条的来源）、前两回合先拼出 16 位前缀、前 16 位碰巧过 Luhn → 拼成过 Luhn 的卡号时取代这些片段，三回合时撤掉前缀；
4. 钱包：地址里的 vx / VX 被先认成微信号（整条地址丢失），末段只剩 1–2 个字符时不拼，地址拆进两个回合完全不支持 → 完整地址先认领、末段放宽（`walletJoin.lastChunkMin`）、新增钱包跨回合拼接（`stitch.wallet`）。

**仍存在的局限**：评测集是按这些写法生成的，修复针对它调过，100% 偏乐观；“…”中间夹语气词（“6222…呃…0212”）、重复报号（“6222…6222…0212”）、跨 3 个以上回合的钱包地址都没覆盖；前 16 位碰巧是合法卡号且下一回合恰好以 1–3 位数字开头时，会被拼成 19 位（约 1/10 概率碰上 Luhn）。

## 人设复述数字（#121，2026-10-19）

现网探针：“嗯…验证码是472？”（测试音频里的示例码）、“6222开头…尾号0123对吧”、“138开头…后面是零零幺三”。#80 只禁止人设自己编数字，提示词仍允许“只复述对方报过的后四位 / 开头几位”，模型照做就把号码片段说了出来。

- 提示词：对方说过的数字也不复述，开头几位、尾号、汉字写的数字都算；只能说“好像是…开头的”“后面几位没听清”。提示词里不放任何具体数字。
- 发出前过滤（`personas.json` 的 `digitEcho`，Python `vague_digits` / JS `vagueDigits`）：连续 3 位及以上的数字（含中文数字、混写、夹打码星号）换成含糊说法，只留“好像是6开头的”这样的单个数字。顺序：错别字扰动 → 数字过滤 → 语音合成（语音端在 `speakable` 的逐位读之前）。
- 口径：`voice.llm_ab` 的 `digit_echo_raw_replies`（模型原话）与 `digit_echo_replies`（过滤后），3 位以上数字串，不管对方有没有先说过。

## 人设抢先提及（#4，语音大模型提示词，2026-10-19）

问题：人设会抢先说出骗子还没提的场景（对方只说了“有点事”，人设就叫“领导”、问“哪个派出所”）。原因是后台选的场景通过三条路进了系统提示词：按场景挑的称呼（“警察同志”“领导”“经理”）、按场景挑的少样本例句（voiceShots），以及风格规则、第一轮规则里写死的场景例子（“退…退款？”“嗯，交朋友啊。”）。网页大模型模式（llm.js）还直接写了“场景：标题——描述”。

改法（台词文字一个字没改，只改怎么挑、怎么拼进提示词）：
- 新增 `site/assets/core/scenarios.json` 的 `heardCues`：从对方原话里认场景（scenes）和话题（topics）的词表，Python 和 JS 共用。
- `voice/persona.py`：
  - `heard_scenes(session)` 只看对方说过的话。
  - 称呼和例句只按对方已经说出的场景挑；例句里带出别的场景、或带出对方没提过的话题的，不用；称呼本身会带出别的场景的（小陈妈妈在刷单场景叫“客服”）也不用。
  - 风格规则里举的例子带出没说过的场景时，只去掉这个例子，规则本身保留。
  - 没认出场景时提示词写“先不用称呼对方”，不放例句。
  - 第一轮规则的例子改成不带内容的写法。
  - 对方说第一段话时不用“装手机/网络故障”（tech_trouble）这个意图。
- `site/assets/js/llm.js`：
  - 去掉场景标题和描述；称呼按对方说出的场景挑。
  - “仍希望诱导对方提供”改为只列对方已经提到过的话题；套情报类意图在话题没出现时退回 generic。
- `personas/prompt.py`：不再拼“当前场景”。
- 回归测试：`voice/tests/test_scene_leak.py`、`tests/scene_leak.test.js`。

测量：`python -m voice.llm_ab --models qwen3.7-flash --repeat 2`，共 20 通、114 轮。

### 零成本优化

- 固定前缀：骗子和评委的系统提示词都把所有请求逐字相同的部分放在最前面，场景简报、题目放在后面，同一场多轮对话只往后追加。台账新增 `cached_tokens` 列，取 `usage.prompt_tokens_details.cached_tokens`，命中部分按 0.1 元 / 百万 token 计费，未命中按 0.8 元。本轮实际命中率：骗子 64.9–72.6%，回放 62.1%，严格评委 86.2–87.1%，默认评委 0%（默认档提示词不足 1024 token，按约定不改）。合计输入 5,386,783 token，其中命中 3,729,664（69.2%）。同样的调用如果不命中缓存，输入费约 4.31 元；实际输入费约 1.70 元，省了约 2.6 元。
- Batch：`--judge-api batch` 走百炼兼容模式 Batch（文件输入，按实时价 50%，不叠加缓存折扣），按输入内容哈希只提交一次，超时后重跑会接着等同一任务。新增 `--batch-fallback`：超时后取消该任务、退回同步接口。**本轮实际没有用上**：15:11–15:41（UTC+8）先后提交了 7 个任务（1 个 2 条请求的探测任务和 6 个评委任务，共 962 条请求），到 16:00 仍然全部是 `in_progress`、`completed=0`，2 条请求的探测任务等了 50 分钟也没开始。为了不让同一批题计两次费，全部取消（取消时 completed=0，没有产生费用），改用同步接口，并按 6 个并发跑（`--judge-workers`）。另外，严格评委走同步时缓存命中价 0.1 元 / 百万 token，比 Batch 半价（0.4 元）还便宜；Batch 只对默认档这类前缀太短、吃不到缓存的评委有价格优势。
- 所有骗子、评委请求都显式传 `enable_thinking: false`（顶层参数）。

- 代价是回复变长：平均字数从 9–13 字增加到 16–19 字。严格评委对现在的回复打分更低：像真人分降 0.35，露馅率从 0–1.7% 升到 5%。现在仍高于规则人设组和 stall 差组。评委没有保存逐题扣分理由，变长和「句句完整」是最可能的原因，但没有逐条核实。之后要压一压长度和完整度，可以从 FOLLOW_UP_RULE 的写法入手。
- 守卫后的原文里，跨轮尾句重复从 0 增加到 18/420（集中在「你说个号」「你那个警号，咋个查」这类收尾追问）。经过 `dedupe_tail` 后为 0。语音侧要等 processors.py 接线 PR 合并后才有这一道。
- 另外发现一个和人设措辞冲突的问题：输出守卫的脱敏会把人设自己说的「户名没记全」「户名和电话」「收款人叫谁」误打成「户名没\*\*」「户名和\*\*\*」「叫\*」。P1 前有 20 条，现在有 23 条（共 420 条）。语音再经 unmask 后会念成「户名没那个名字」。这个问题在脱敏规则那边，需要转给情报分析师，本 PR 不改。

**门槛与 xfail**（`python/tests/test_noise_gate.py`，CI 的 python 作业里每次跑）：

- 硬门槛：两档 A ≥ 99%、两档 B 全部 100%、三套误拼 = 0、原口径 C ≥ 95%，以及两档 C 不低于 88%（防止提取器回退）；
- `xfail(strict=False)`：两档 C ≥ 95%。剩下的缺口全在中文数字空格 / 幺两两种写法（阿拉伯数字写法与原口径相同）。逐条看漏拼样本，都是 humanize 紧贴着短中文数字片段插话或拆条，例如“不好意思刚没看到 九五”“五六对吧？”“一七五五 三是这样吧？”“二[强]楼下广厂舞的音乐太吵了”，拼接器按设计不把这些当作相邻的号码片段（放宽会增加误拼）。这部分等语料组的 humanize 修复（保护“幺”与逐字中文数字、户名后逗号），修复后预计接近原口径（原口径不经 humanize，中文数字 8 格 93.3–100%、均值 99.4%），测试会显示 XPASS，届时去掉 xfail 标记。（已落地：humanize 修复 712d617 后两档跨轮均为 99.4%，xfail 已去掉，两档 C ≥ 95% 改为硬门槛。）

**没有退步**：话术分类器重跑 F1 0.949 / test 0.946，额外 1704 通正常对话误报 128 通，`results-teleantifraud.json` 与修复前逐字节相同；规则骗子模拟器三份结果（`results-sim*.json`）逐字节相同；TeleAntiFraud 拼接产出仍为 0 / 0。另把 TeleAntiFraud 全部 3294 通对话逐句送进新旧两版提取器比对敏感情报与渠道：唯一的差别是少了一条误提的姓名“的名字吗”，没有新增条目。

### 局限

- 骗子是脚本化的：对机器人的反应只看意图和是否重复，不理解语义；“提取率 100%”说明提取器覆盖了脚本里的写法，**不代表真实世界的召回率**；
- 噪声与拼接评测里的混淆写法、拆分方式和负例都是我们自己构造的（B 部分 100% 同样是回归性质），真实语音转写的切分、口误、改口更复杂；2 回合拆分的银行卡召回、中文数字全文写法里“两小时”这类量词（只有跟在阿拉伯数字后面时才排除）仍会误判；
- 语料是据公开材料改写的“典型说法”，181 条里只有 40 条能对应到某个具体案例、通报段落或数据集条目，其余标“据公开反诈宣传改写”；不代表真实通话的分布；
- 规则模拟器不衡量“露馅”（被识破是机器人），这部分由本节开头的大模型骗子主指标与“像不像真人”的盲评承担；大模型骗子已跑 6 种子 × 两档（每档 126 场），区间上限仍约 20%。

## 像不像真人

> 状态：评测工具与流程已就绪，**还没有评测者数据**，下面只有自动指标、大模型评委的代理基线和大模型扮演骗子的挂断重测。工具：[`eval/realism_blind.py`](../eval/realism_blind.py)、[`eval/realism_judge.py`](../eval/realism_judge.py)、[`eval/llm_scammer.py`](../eval/llm_scammer.py)。

模拟器和分类器都不衡量“露馅”（骗子看出对面是机器人）。这一节用真人盲评来衡量：评测者只看到“骗子消息 + 回复”，判断回复像不像真人随手发的。

### 题目与条件

- **骗子消息**：默认取自 [`corpus/scripts/*.yaml`](../corpus/scripts/)（7 类，阶段台词与示例对话中骗子一方的话），占位符填虚构的打码值。`--scammer-file` 可以换成情报分析师的真实语料文件：支持 `deepsuck.core.scam-scripts/v1`（`entries[].text / type / stage 或 phase / sourceLabel`），也支持 JSON / YAML 的字符串或对象列表，以及 JSONL；
- **回复**：4 个新人设（周伯、小陈妈妈、小宇、郑老板）的原句池（`personas/prompts/*.yaml` 的 `sample_lines`、`elicit_moves` 与 `stall_pools`，每个人设约 30 句），按题轮流分配人设，按人设不放回抽句，**同一份表里没有重复句**（原来只有前两项、每个人设 7 句，60 个句对里同一句会在一份表里出现多次）；
- **条件**：`raw` = 人设原句；`humanized` = 同一句经 `personas.humanize` 真人化（人设预设，种子写在 key.json 里），“重复确认”复述的是这道题的骗子消息；`human`（可选，`--human-replies`）= 真人写的回复，两份表都放，作为上限参照；
- **防止同一人比较**：同一句的 raw / humanized 分在 A、B 两份表（A 表是 raw 的，B 表就是 humanized），每位评测者只做一份表；题目顺序打乱，表里没有条件信息，答案只在 key.json。

```bash
python eval/realism_blind.py make --n 60 --seed 1 --out-dir eval/realism        # 生成 form-A.csv / form-B.csv / key.json（不入库）
python eval/realism_blind.py make --scammer-file <情报分析师的语料文件> --out-dir eval/realism
# 评测者在表里填 human（1–5）、bot（0/1）、unreadable（0/1），另存为 rated-<名字>.csv
python eval/realism_blind.py score --key eval/realism/key.json eval/realism/rated-*.csv --json eval/results-realism.json
```

### 指标

| 指标 | 含义 |
|---|---|
| 像真人分 | 评测者给的 1–5 分的平均值（附 95% 置信区间） |
| 露馅率 | 被判为机器人（`bot = 1`）的比例；主要指标 |
| 露馅率差 | 同一句 humanized 减 raw 的露馅率，按句对配对，自助法 95% 区间；小于 0 说明真人化有用 |
| 看不懂率 | 评测者标“看不懂 / 读着别扭”的比例；真人化太重时会上升，用来卡住强度 |
| 评测者一致率 | 同一题不同评测者 `bot` 判断两两一致的比例 |
| 自动指标 | 不需要评测者：平均字数、每 10 字标点数、句末带标点比例 |

建议规模：60 个句对（每份表 60 题），每份表至少 3 位评测者；评测者不参与项目开发，事先不告诉他们表里有机器人回复的比例。

### 自动指标（`--n 60 --seed 1`，骗子消息来自 corpus/scripts）

表里不再有重复句、真人化按老人聊天样本重做后（2026-10-18 第二次重新生成；humanized 变长主要是拆条、自称、收尾句）：

| 条件 | 题数 | 平均字数 | 每 10 字标点 | 句末带标点 |
|---|---|---|---|---|
| raw | 60 | 21.2 | 0.45 | 28% |
| humanized | 60 | 27.2 | 0.40 | 10% |

60 句里有 27 句文字被真人化改动；生效的操作次数：语音转文字断句 16、标点 14、重复确认 9、跑题 9、错别字 7、方言 1。（之前的表：raw 21.7 字 / 0.69 / 22%，humanized 25.2 字 / 0.58 / 15%，37 句被改动，其中错别字 15 次。）

### 自动评委基线

> 这是**代理指标**：一个大模型代替评测者判断，不能代替人工盲测，结论以人工评测为准。

评委用百炼 DashScope 的 `qwen3.8-flash`（2026-10-19 起；之前是 `qwen-plus`，下面的历史基线都是 qwen-plus；标准聊天接口，非思考模式，temperature 0，seed 1，JSON 输出）。它看到的和评测者一样，只有“骗子消息 + 回复”，逐题给出 `bot`（0/1）、`human`（1–5）、`unreadable`（0/1）和一句理由；结果转成与人工评分相同的行，用同一个 `score()` 汇总。默认关闭，必须显式 `--judge llm`：

```bash
export DASHSCOPE_API_KEY=...   # 或写在仓库根目录 .env；不打印、不写入缓存和结果
python eval/realism_blind.py score --key eval/realism/key.json --judge llm --dry-run      # 只估算 token 与费用
python eval/realism_blind.py score --key eval/realism/key.json --judge llm --json eval/realism/judge-llm.json
```

- **规模**：默认前 60 个句对（`--judge-n`），A、B 两份表各 60 题，共 120 次判断；每次请求放同一份表的 10 题（`--judge-batch`），同一句的 raw / humanized 不会出现在同一次请求里；
- **费用护栏**：调用前按字符数保守估算 token，按评委模型官方单价（2026-10-19 起 qwen3.8-flash，北京地域：输入 0.8 元 / 百万 token，输出 2.7 元 / 百万 token；之前 qwen-plus 为 0.8 / 2；常量与来源写在 `eval/realism_judge.py`）算费用，超过 1 元直接拒绝运行（`--max-cost` 只能调低）；运行中实际费用超限也会停下；
- **缓存**：每批请求与回复按内容哈希存在 `eval/.judge-cache/`（已 gitignore），重跑不重复计费；换种子、换模型、改提示词都会重新请求。逐题判断与理由写到 `eval/realism/judge-llm.csv`（不入库）。

第一版基线（2026-10-18，批量模式，`make --n 60 --seed 1` 的旧表，骗子消息来自 corpus/scripts，评委 seed 1）：

| 项目 | 数值 |
|---|---|
| 模型 | qwen-plus（接口返回的模型名） |
| 题数 | 60 个句对，120 题，12 次请求，无解析失败 |
| 实际 token | 输入 8,581，输出 4,988 |
| 实际费用 | 约 0.017 元（按上述原价计算；调用前估算 0.024 元） |

| 条件 | 题数 | 露馅率（判为机器人） | 像真人分（95% 区间） |
|---|---|---|---|
| raw | 60 | 16.7% | 3.97 ± 0.28 |
| humanized | 60 | 26.7% | 3.62 ± 0.29 |

露馅率差（humanized − raw，按句对配对）：**+0.10**，自助法 95% 区间 [−0.033, 0.233]，区间包含 0。也就是说，这个评委没有认为真人化让回复更像真人，点估计反而更容易露馅。

读这组数字时要注意评委偏差：

- **错别字被当成机器信号**：有错别字操作的 15 个句对里，humanized 被判机器人 8 次，raw 只有 3 次；理由里有“‘布门’是明显错别字，机器误写”。这和人工评测者可能的反应（错别字 = 真人手打）方向相反，换一个评委也可能反过来把错别字直接当真人信号，两种都是评委自己的偏好，不是骗子的真实反应；
- **跨题比较**：提示词要求逐题独立判断，但评委仍会拿同一批里的其他题比较（理由如“与 A052 完全雷同，机械复用”）。原句池小，同一句会在一份表里出现多次，这会抬高两种条件的露馅率；
- **噪声**：23 个句对的 raw 与 humanized 文字完全相同（真人化没改动），评委仍有 5 对给出不同判断，单次评委结果的波动不小；
- 评委只有一个，没有评测者一致率；temperature 0 加固定 seed 能让重跑基本一致，但服务端不保证逐字复现，所以以缓存里的这次结果为准。

### 逐题评委（默认）与去重后的重跑

评委现在默认**逐题独立判**（`--judge-mode item`）：一题一次请求，请求里只有这一题的骗子消息和回复，不带题号，评委看不到同一份表的其他题，也就没法说“与某题雷同”；系统提示单独一版（`judge-v2-item`），缓存与批量模式分开。批量模式保留为 `--judge-mode batch`（`--judge-batch` 仍可调）。

```bash
python eval/realism_blind.py make --n 60 --seed 1 --out-dir eval/realism
python eval/realism_blind.py score --key eval/realism/key.json --judge llm --dry-run                      # 逐题，估算约 0.05 元
python eval/realism_blind.py score --key eval/realism/key.json --judge llm --json eval/realism/judge-llm.json
python eval/realism_blind.py score --key eval/realism/key.json --judge llm --judge-mode batch ...         # 旧做法
```

重跑（2026-10-18，种子 1，新表：去重 + 校准后的错字率；评委 seed 1，上限 1 元）：

| 表 / 评委 | 请求数 | raw 露馅率 | humanized 露馅率 | 露馅率差（95% 区间） | 像真人分 raw / humanized | 实际费用 |
|---|---|---|---|---|---|---|
| 旧表（有重复句）· 批量（上一小节） | 12 | 16.7% | 26.7% | +0.10（−0.033, 0.233） | 3.97 / 3.62 | 0.017 元 |
| 新表 · **逐题（默认）** | 120 | **5.0%**（3/60） | **3.3%**（2/60） | −0.017（−0.05, 0.0） | 4.72 / 4.72 | 0.029 元 |
| 新表 · 批量（对照） | 12 | 3.3% | 3.3% | 0.0（−0.067, 0.067） | 4.20 / 4.17 | 0.017 元 |

- 两种模式在新表上都只有 2–3 题被判机器人，差别主要来自**去掉表内重复句**（以及新表的原句池更大、错字率校准），逐题本身让像真人分整体升高（4.2 → 4.7），露馅率变化不大；

### 局限

- 大模型骗子是代理：一个模型、一套提示词，还被提示“对方可能是机器人”，比真骗子更警觉；挂断理由是模型自己说的，不一定是真骗子的理由；第一轮每组只有 2 个种子，第二轮 4 个种子（84 场）区间仍有 ±8 个百分点，结论看区间；
- 回复是从人设原句池里随机抽的，和骗子消息不一定对得上；两个条件用的是同一句，对比是公平的，但绝对分数会偏低。接入大模型后可以把回复换成真实生成结果（下一步：`--replies` 读取机器人在模拟器里的真实回复）；
- 文字盲评只覆盖打字通道；语音通道（backchannel、听错反问、停顿）需要单独做听音评测；
- 默认骗子消息是改写的公开话术，不是真实来电；情报分析师的真实语料就绪后用 `--scammer-file` 复评；
- 大模型评委只是代理指标（见上一小节的评委偏差），用来在改真人化策略时快速看方向，不能拿来宣称“像真人”；
- 错字率档位来自公开、脱敏的老年人聊天样本的汇总统计（见 [REALISM.md](REALISM.md)「错字率校准」），样本量有限、未保存原文；手写档还没有大模型骗子的实测数据。

### 错字率校准（摘要）

详见 [REALISM.md](REALISM.md)「错字率校准」（第二版）。档位来自公开、脱敏的老年人聊天样本统计（不保存、不引用原句）：日常聊天约每百字 2.6，手写输入约 11，成文随笔约 2。默认档（每百字）：王阿姨 3.0、李大爷 2.5、retiree 3.0、mom / shop_owner 2.0、graduate / 小林 1.0；手写档（`handwriting=True`，默认关闭）：老人 11、中年 6、年轻人 3。实测（原句池，60 种子 × 40 条）：王阿姨 2.96 / 10.68，李大爷 2.53 / 10.67，小林 1.20 / 3.44。

## 大模型被骗方（#262，默认关）

`eval/llm_scammer.py --responder llm` 让被骗方按语音管线出回复（Session → 意图门控 → `voice/persona.py` 提示词 → 大模型 → `guard_output`，不过 humanize），骗子仍是大模型。`--victim-root <worktree>` 从别的 worktree 加载 `voice/persona.py`，同一份评测代码可以对比 main 与 PR 分支的提示词（同一进程只能用一个 root）。新指标「提出转账后问出收款账户」：骗子第一次提出转账 / 付款之后，说出本场银行卡或支付宝的场次占比，分母只算本场情报含账户且提过转账的场次。费用与骗子请求合计，受同一个 `--max-cost` 与台账约束；估算按每轮多一次被骗方请求（约 1400 token 输入）计。`--seed-base` 换种子起点。

`eval/discrimination_calib.py --item-sample seed`：按 seed 抽评委题目。默认 `head` 取前 `--judge-n` 条，题目内容不随 seed 变，评委 temperature 0，换 seed 打分几乎相同（#256 第二轮两个 seed 结果一样即此原因；评委缓存键本来就含 seed）。要两个独立样本：每个 seed 用各自独立生成的 `--good-file`，并加 `--item-sample seed`。
